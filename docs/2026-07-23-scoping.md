# Shape Profiler — landscape research + scope

*A privacy-preserving data profiler: capture how a dataset behaves — never what it contains — so an agent can model it.*

Drafted 2026-07-23. Research: 6-agent web sweep over profilers, CLI tools, PII/PHI detection, dbt/Snowflake scaffolding, and privacy/sketch techniques (~42 tools evaluated, claims verified against docs/source).

---

## 1. The one-paragraph verdict

Nothing ships this today. Every mature profiler leaks raw cell values in its default output; every value-free tool is schema-only with no behavioral statistics; nothing does data-driven foreign-key candidate detection from files; and nothing generates dbt/Snowflake scaffolding from a *local file* profile. The profiling math itself is ~90% commodity — the defensible product is the **output contract** (zero raw values, by construction, sized for an LLM context window) plus the **combination**: behavioral stats + semantic PII/PHI typing + value-shape masks + FK candidates + dbt/Snowflake artifact generation, in one local-first CLI. Someone tried the closest architectural precedent (piicatcher: name+value detection, tags-only output, warehouse connectors) and it was archived in January 2026. The framing has no owner.

## 2. Landscape: what exists and why it doesn't solve this

### 2a. The profilers all leak

Verified against docs/source — raw cell values in **default** output:

| Tool | How it leaks by default | Redaction story |
|---|---|---|
| ydata-profiling | Sample rows, duplicate rows, categorical frequency tables, min/max | `sensitive=True` kills samples/duplicates only; freq tables + extremes survive; docs warn it "doesn't guarantee privacy" |
| Capital One DataProfiler | `data_stats.*.samples` in every report, min/max, category values | Post-process the dict yourself (`omit_keys`); no first-class suppress flag; PII labeler needs TensorFlow |
| whylogs | Frequent-items sketch stores literal strings; min/max are raw; serialized KLL sketches retain actual input values | Per-column metric exclusion via `DeclarativeSchema` — opt-out, not a guarantee; maintenance stalled (last push Jan 2025) |
| Deequ / PyDeequ | Full value histograms on low-cardinality columns; min/max | Requires Spark/JVM anyway |
| Great Expectations | `partial_unexpected_list`: up to 20 raw failing values in default SUMMARY results | Configurable to BOOLEAN_ONLY; profiling was dropped in GX 1.x |
| Soda Core | Frequent values + extremes shipped to Soda Cloud; 100-row failed-row samples | Config flags; profiling value is SaaS-attached |
| qsv (`stats`/`schema`) | min/max/mode/antimode raw; schema embeds enum lists of actual values (cardinality ≤ 50) | None; docs say pre-filter sensitive columns yourself |
| DuckDB `SUMMARIZE` | Raw min/max including VARCHAR columns | The engine can compute safe aggregates instead — leak is in the convenience view |
| xan, Miller, csvstat, sqlite-utils | min/max/mode/lex_first/lex_last/most-common values | None / partial flags |
| dbt-profiler | min/max raw (lexically first/last email, SSN…) into dbt docs | None |
| OpenMetadata / DataHub | 50 sample rows per table by default / `include_field_sample_values: true` default | Configurable off; platform-shaped |

The pattern is universal: **privacy is opt-out configuration, never a contract.** whylogs is the closest architecture (compact, mergeable, sketch-based, machine-readable) and it still leaks three ways by default — WhyLabs' own security docs admit it.

### 2b. The value-free tools are shallow

- **frictionless describe** — genuinely zero-leak output, but schema-only: no cardinality, nulls, uniqueness, distributions. "The proposed tool ≈ frictionless's privacy posture + qsv's depth + things neither has."
- **datacontract-cli** — the closest existing *file → dbt scaffold* bridge: imports CSV/Excel/Parquet/SQL into an ODCS contract, exports `dbt-sources`, `dbt-models`, `dbt-staging-sql`. No statistics, no PII typing, no FK detection. Strong interop target (emit ODCS, inherit their exporters).
- **dbt-codegen / dbt-coves / SQLMesh create_external_models** — generate exactly the right artifacts but only by introspecting tables *already in the warehouse*. Natural downstream consumers, not competitors.
- **Snowflake native** — `INFER_SCHEMA` + `CREATE TABLE USING TEMPLATE` (value-free typing of staged files) and `SYSTEM$CLASSIFY` (value-free semantic/PII classification: `semantic_category`, `privacy_category`, `confidence`, `coverage`). Together ~60% of the idea — but post-staging (PII already landed), Enterprise-gated for classification, no dbt artifacts, no Excel, no FK detection. `SYSTEM$CLASSIFY`'s output schema is the best existing template for value-free semantic typing.
- **dlt** — local schema inference → value-free YAML → dbt generator, but schema emerges as a side effect of *loading the data somewhere*; no stats, no PII, no masks.

### 2c. Detection engines are reusable; none is a profiler

- **Presidio** (active, 10k★) — recognizers = regex + context words + checksums; `RecognizerResult` carries only entity_type/offsets/score, never matched text. Best-maintained detection pack to embed. `presidio-structured` already maps columns → entity types.
- **python-stdnum** (active) — Luhn/Verhoeff/ISO-7064 + US SSN/EIN/ITIN/RTN validators. Confirmed: **no NPI or DEA modules** — both are small, well-documented algorithms to hand-write (NPI = Luhn over `80840`-prefixed 9 digits; DEA = 2 letters + 7 digits with its own check-digit formula). Checksum pass-rates give near-zero-false-positive flags with zero value exposure.
- **ICD-10** — regex shape overmatches badly; pair with official code-list membership, report only match rate. **MRN** — no national format exists; detection must combine column-name tokens + shape masks + uniqueness + neighboring healthcare columns — *exactly what a shape profiler does better than value-regex tools*.
- **Taxonomy references**: GCP DLP infoTypes (US_HEALTHCARE_NPI, MEDICAL_RECORD_NUMBER, ICD10_CODE…), HIPAA Safe Harbor's 18 identifiers (maps directly to flags like "zip granularity", "date granularity", "MRN-like unique numeric"), SDV's sdtype vocabulary.
- **Prior art for shape masks**: DataCleaner's Pattern Finder (letters→`A`, digits→`9`, frequency counts) — study its tokenization rules before reinventing. Talend DQ ships the same idea commercially.

### 2d. FK-candidate math is off the shelf

- **datasketch** (active, v2.0.0 Jul 2026): MinHash + **LSH Ensemble** answers "which columns largely contain this column" at scale — the right index for multi-tab workbooks and whole schemas.
- **Apache DataSketches**: theta-sketch intersections + `theta_jaccard_similarity` for tighter-bounded pairwise overlap/containment. (HLL unions well but intersects poorly — use theta when containment matters.)
- Exact inclusion-dependency discovery (BINDER/SPIDER, Metanome) defines the accuracy ceiling; sketch containment is the practical approximation. Microsoft patented HLL-based join-column detection — established practice.
- **SchemaSpy precedent**: FK candidates from *naming conventions* alone. Combine name evidence + type compatibility + containment score for ranked candidates.

### 2e. Two findings that sharpen the design

1. **The counter-position is real.** Snowflake's Cortex Analyst semantic model *mandates ≥25 raw sample values per dimension* because samples improve LLM text-to-SQL accuracy. qsv's `describegpt` sends top-10 raw frequency values to the LLM by default. The mainstream is resolving accuracy-vs-privacy in favor of samples. This tool takes the opposite bet — so it must demonstrate that **masks + cardinality + semantic types + enum shape recover the modeling accuracy that samples provide**. (For *landing-table scaffolding* — as opposed to text-to-SQL — that bet is very winnable: DDL decisions need types, nullability, precision, keys; not values.)
2. **"Aggregates only" is not a formal privacy guarantee, and the design must reflect it:**
   - min/max **are** raw cell values — the single most common leak in every tool above.
   - Serialized sketches leak: KLL retains actual inputs; HLL/theta/MinHash permit membership inference (Desfontaines et al., PoPETs 2019); FTC (reaffirmed 2024): hashing ≠ anonymization — low-entropy domains (SSNs, phones) are dictionary-attackable. **Sketches stay in a local cache; only derived scalars enter the profile.**
   - Formal DP (OpenDP/SmartNoise) is practical for counts but overkill here — noise on a null rate changes no dbt decision. The defensible posture: **structural suppression rules + an honest threat model**, not a privacy proof.

## 3. Proposed scope

*(Revised after an adversarial review pass; the review's findings are folded in below.)*

### 3a. Positioning and identity

> A CLI that turns any dataset — CSV, multi-tab Excel, Parquet, or a database — into a compact, machine-readable profile of its *shape* (types, nulls, cardinality, patterns, PII/PHI flags, key candidates) with **no raw values, by construction**, so an LLM agent can model the data it is never allowed to read.

**Identity decision: the agent is the scaffolder; the profile is the interface.** The differentiated bet is that Claude reading `profile.json` produces better dbt/Snowflake scaffolds than Claude reading `head -50` — not that silueta's own templates beat dbt-codegen's. Deterministic emitters (v0.2) are a convenience baseline and a benchmark, not the product. Consequence: the profile schema optimizes for LLM legibility and **a hard token budget** — target ≤ ~1.5k tokens per table at default verbosity, with `--full` for the exhaustive version; a 40-sheet workbook must fit in one context window.

**The adoption criterion** (from the review, and it's right): the tool gets *permitted* because of the safety contract, but it gets *used twice* only if `silueta scan vendor.xlsx` gets the **types right on dirty data** — first shot, no hand-editing the resulting DDL. v0.1 is organized around that, not around PII taxonomy breadth.

**Name: `silueta`** (the silhouette — outline without the detail). Confirmed available on PyPI 2026-07-23; **personal OSS** under `chekos/silueta` (motivated by work frustration, built as a generic public tool with no employer specifics).

**Distribution: "just works everywhere" is a stated requirement.** An agent (or a colleague) should get from zero to `silueta scan file.xlsx` in one command on any machine:
- v0.1: `uvx silueta` / `uv tool install silueta` / `pipx install silueta` — zero-setup for anyone with uv, which includes every Claude Code environment.
- Later: a Homebrew tap (`brew install chekos/tap/silueta` via a pyapp/shiv-style bundled binary) and possibly `npx`-reachable packaging if agent ecosystems demand it. The constraint this puts on v0.1: keep the dependency tree small and pure-wheel (duckdb + typer + openpyxl all ship wheels) so every packaging route stays viable.

### 3b. The safety contract (the license to operate)

The profile **never contains**:
- raw cell values, sample rows, or frequent-value lists
- min/max for strings, dates, or identifier-like columns (numeric range reported as order-of-magnitude + precision/scale/fits-in-int32/64 — everything DDL needs, nothing more; date spans at year granularity, and ages capped per HIPAA Safe Harbor's 90+ rule — the tool applies Safe Harbor to *its own outputs*, not just as flags on the data)
- serialized sketches, hashes of values, or regex captures
- any statistic derived from a value observed in fewer than *k* rows (default k=5): masks roll up to coarser masks, distinct counts get reported as ranges. This is **value-level** k-suppression, not just row-level — a 2-distinct-value column where one value covers a single row must not expose that value's mask/length/charset.

Explicitly handled edge cases (each was a hole in the first draft):
- **Constant / near-constant columns**: reported as `constant: true` + physical type only — no mask, length, or charset (mask + length + entropy-0 + a column name like `state` can pin the value).
- **Files/sheets smaller than k** (3-row lookup tabs are common): profile reports structure only (names, types, row count) and marks stats `suppressed_small_table` — defined behavior, not accident.
- **Headers and sheet names are scanned, not trusted**: pivoted workbooks put data in headers (`2024-01`, provider names as columns) and PHI shows up in sheet names. Tier-2 validators run on header/sheet-name tokens too; a `header_looks_like_data` alert fires and those tokens are masked in the profile. `--redact-names` exists for fully-sensitive headers but is documented as incompatible with `emit` (a scaffold needs column names) — it emits positional placeholders instead.
- **`diff` output** (v0.3) is itself k-suppressed — two profiles of consecutive vendor drops differing by one row can single that row out via deltas; the threat model covers the diff surface explicitly.

Threat model, stated honestly and *embedded in the artifact* (a `_contract` field in profile.json, so it travels when pasted): protects against **accidental context leakage** — values entering an LLM conversation, a log, a ticket. It does **not** claim formal anonymity against an adversary reconstructing small populations from aggregates; the phrase is "no raw values by construction," never "private" or "anonymized."

`silueta verify` is an **internal regression suite**, not a user-facing trust ritual: it re-scans emitted artifacts (profile.json *and* generated sources.yml/DDL/descriptions) for source-value token matches across a test corpus. As a user command it would be noisy ("2024", "true", "M/F" collide constantly) and can't catch inference leaks anyway — advertising it as proof would train false confidence. The trust story is the contract + test suite, not a canary button.

The Macie precedent stands: value disclosure, if ever added, is a separate explicit command — never a flag on the profiler.

### 3c. Architecture

- **Python package, uv-native** (`uvx silueta scan …`), typer CLI.
- **DuckDB as the scanning/stats engine**: CSV sniffing (`sniff_csv`), native Parquet, larger-than-memory aggregates, later `ATTACH` for SQLite/Postgres/MySQL. Compute *only* safe aggregates in SQL — never `SUMMARIZE`. **Plus openpyxl (or equivalent) for workbook structure** — honest amendment: DuckDB's `read_xlsx` won't see merged cells, sheet enumeration quirks, or `.xls`, and messy-workbook recovery needs cell-level access. Two dependencies, not one; `.xls` support decided in v0.1 (likely: convert-or-decline with a clear message).
- **Messy-tabular recovery is a first-class stage** (the adoption-critical one): table-region detection (skip title/footer rows), header-row inference incl. multi-row headers, typed-as-text recovery (numerics/dates stored as strings, Excel serial dates), per-column `type_confidence` and `witnessed_types` (xan's pattern) rather than a silent VARCHAR collapse. Built against an ugly-workbook test corpus from day one.
- **Semantic typing, two-tier** (piicatcher's architecture, resurrected): tier 1 = column-name token rules (no data touched); tier 2 = in-process value validators — regex + context + checksum (Presidio-recipe), emitting only `{type, match_rate, checksum_valid_rate, confidence}`. Validators: python-stdnum + hand-written NPI/DEA + ICD-10 code-list + zip/zip+4, phone, email, UUID, date formats, credit-card Luhn. Taxonomy: DLP-style names, HIPAA Safe Harbor-aligned PHI tier. **Sampling is a recall question, not a performance question**: validators sample *non-null* values with a minimum floor, and any checksum-valid hit of a high-severity type (SSN, MRN-like, DEA) raises an alert regardless of match rate — sparse PII (95%-null SSN column) is exactly what must not slip through.
- **Shape masks**: DataCleaner-style tokenization (digit→`9`, upper→`A`, lower→`a`, punctuation literal), top masks + coverage % under value-level k-suppression.
- **FK candidates — exact first, sketches later**: at workbook scale (< ~1M distinct values) exact containment is one DuckDB anti-join over distincts — exact, no extra dependency, no sketch cache, none of §2e.2's sketch-privacy mitigations needed. Rank by containment × name-similarity × type-compatibility, with a cardinality floor so low-cardinality enums (state, status, M/F — "contained in" everything) don't dominate. datasketch/LSH-Ensemble arrives in v0.3 where it's justified: cross-database scale.
- **Outputs**: `profile.json` (versioned stable schema, token-budgeted — the agent contract), `report.md` (human). Scaffold artifacts in v0.2 (see open question on ODCS below).
- **Red-flag alerts** (the "99,998 of 100,000 unique" instinct): near-unique non-key columns, constant columns, mixed casing regimes, type-consistency below threshold, PII flag on unexpectedly-named column, ID-like column across multiple sheets (join hint), zip granularity finer than Safe Harbor, header-looks-like-data, sheet-not-tabular.

### 3d. Milestones

**v0.1 — profile files, survive real workbooks.** CSV + XLSX (multi-sheet) + Parquet → `profile.json` + `report.md`. Headline capability: messy-Excel type/header recovery (table region, header inference, text-typed numerics/dates) with type confidence. Per-column: physical type + consistency, nulls/blanks, cardinality + uniqueness, length/casing/charset, shape masks, semantic flags, alerts. Workbook-level: exact-containment FK candidates, name-convention analysis. Safety contract enforced + `verify` regression corpus. **Exit test: profile 5 genuinely ugly real-world workbooks; generated types need zero hand edits.**

**v0.2 — scaffold (gated).** Gate: the head-to-head from open question 4 — Claude + `profile.json` must produce scaffolds at least as good as Claude + raw head. Then `silueta emit dbt|snowflake` (or ODCS → datacontract-cli's exporters, if that resolves cleaner): sources.yml with types + generated column descriptions ("email-shaped, 0.2% null, unique"), staging SQL, Snowflake DDL sized from precision/scale facts. All emitted text passes the verify corpus.

**v0.3 — databases + drift.** DuckDB `ATTACH` (Postgres/MySQL/SQLite) + Snowflake via ADBC: profile schemas in place; sketch-based FK candidates at cross-database scale (datasketch). `silueta diff old.json new.json` — vendor-drop drift detection (schema changed? cardinality jumped? new nulls?), with k-suppressed deltas.

**v0.4 — agent packaging.** Claude Code skill + recommended lockdown config (permission deny on `data/**` for Read *and* a PreToolUse hook for `cat/head/grep` bypass — a known gap, documented in claude-code#6699) + optionally an MCP server exposing `scan`/`read_profile`/`emit`. Note: v0.1 is already agent-usable via Bash — the CLI *is* the agent interface; MCP is packaging, not a prerequisite.

### 3e. Explicitly out of scope

- Deep statistical EDA, correlations, distributions-for-humans (ydata-profiling exists)
- Data cleaning/transformation, synthetic data, anonymization of the data itself
- Formal differential privacy (documented as a non-claim; optional far-future mode)
- Exact n-ary inclusion-dependency discovery (BINDER territory; unary exact containment is in)
- Free-text/document PII scanning (Presidio exists; this is tabular-first)
- Truly non-tabular sheets — dashboards, pivot layouts beyond header recovery (detect, flag `not_tabular`, skip)

## 4. Open questions

*Resolved 2026-07-23: name = `silueta` (PyPI available), personal OSS at `chekos/silueta`, uvx-first distribution with brew/npx ease as a stated goal.*

1. **ODCS vs hand-built emitters**: datacontract-cli already exports dbt-sources/models/staging-SQL from an ODCS contract. Emitting ODCS (+ a stats extension block) might replace v0.2's emitters entirely — resolve by prototyping one workbook through their pipeline before writing any emitter.
2. **The core-bet experiment (gates v0.2)**: same workbook, Claude + `profile.json` vs Claude + raw `head -50`; blind-compare the dbt scaffolds. If the profile loses, the fix is profile content (richer masks/enum shape), not abandoning the contract. If it wins, that's the launch story.
3. **Testing PHI validators without possessing PHI**: build a synthetic corpus (faker + checksum-valid generated NPI/SSN/DEA/ICD) — a real work item, not an afterthought.
4. **Sub-k and tiny-table ergonomics**: is `suppressed_small_table` acceptable for the 3-row lookup tabs, or does it need a documented `--acknowledge-small-tables` loosening? Decide from real use.
